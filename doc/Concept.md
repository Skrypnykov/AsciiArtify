# Concept.md

## Вступ

Команда стартапу готує **Concept проєкту** та обирає інструменти для побудови ефективної системи локальної розробки. У цьому документі розглядаються та порівнюються три ключові рішення на базі Kubernetes: **minikube**, **kind** та **k3d**.

### Мета документу

* **Порівняльний аналіз:** Оцінити технічні можливості, переваги та недоліки трьох інструментів для розгортання локальних Kubernetes-кластерів.
* **Аналіз ліцензійних ризиків:** Дослідити потенційні ризики, пов'язані з комерційним ліцензуванням Docker Desktop.
* **Альтернативні рішення:** Розглянути можливість та доцільність застосування **Podman** як безкоштовної open-source альтернативи.

## Minikube

**Minikube** — це інструмент для запуску локального Kubernetes-кластера на одному комп’ютері. Він ідеально підходить для розробників-початківців, навчання та швидкого тестування базових сценаріїв.

### Переваги
* **Простий старт** та низький поріг входження
* **Чудова документація** та велика спільнота
* **Вбудована підтримка аддонів** (Ingress, Dashboard, Registry тощо) через одну команду
* **Гнучкість у виборі драйверів** (Docker, Podman, VirtualBox, Hyper-V)
* **Оптимальний вибір для PoC** (Proof of Concept)

### Недоліки
* **Повільніший запуск** та вище споживання ресурсів у порівнянні з kind/k3d
* **Менш зручний для CI/CD** конвеєрів
* **Складніше налаштування** складних багатонодових (multi-node) сценаріїв

## kind

**Kind (Kubernetes IN Docker)** — інструмент, який розгортає вузли Kubernetes як звичайні Docker-контейнери. Найчастіше використовується для автоматизації та тестування маніфестів.

### Переваги
* **Дуже швидке створення** та видалення кластерів
* **Ідеальна інтеграція в CI/CD** та автоматизовані тести
* **Легке розгортання multi-node** архітектур
* **Максимальна близькість** до ванільного (upstream) Kubernetes

### Недоліки
* **Критична залежність** від наявності Docker (або детально налаштованого Podman)
* **Відсутність вбудованих рішень** для Ingress або LoadBalancer (потребує ручного конфігурування)
* **Вищий поріг входження** для новачків

---

## k3d

**k3d** — це мінімалістична обгортка для запуску надлегкого дистрибутиву **k3s** у Docker-контейнерах.

### Переваги
* **Найвища швидкість** старту та мінімальне споживання оперативної пам'яті
* **Вбудований Ingress-контролер** (Traefik) та проста робота з портами
* **Чудово підходить для локальних демо** та розробки на слабких машинах
* **Просте керування** multi-node кластерами

### Недоліки
* **Використовує k3s**, а не чистий upstream Kubernetes (деякі компоненти замінені легшими аналогами)
* **Ризик сумісності:** поведінка деяких складних enterprise-додатків може відрізнятися від production-середовища

## Docker licensing risk та Podman

> ⚠️ **Важливо про ліцензування:** Docker Desktop є платним для комерційного використання у компаніях із кількістю працівників > 250 або доходом > \$10 млн. Для стартапу на ранньому етапі це не критично, але цей юридичний ризик варто закладати у стратегію.

### Використання Podman як альтернативи:
* **Повна безкоштовність:** Podman є повністю open-source продуктом і не має ліцензійних обмежень.
* **Сумісність:** Minikube має чудову рідну підтримку Podman (`--driver=podman`).
* **Особливості для kind/k3d:** Вони також можуть працювати з Podman, проте через архітектурні особливості (rootless режим) налаштування є складнішим і менш стабільним, ніж з Docker.

## Демонстрація minikube

Нижче наведено покроковий посібник із розгортання тестового застосунку в локальному кластері.

### 1. Створення кластера
Запустіть кластер за допомогою Docker-драйвера:
```bash
minikube start --driver=docker
```

### 2. Перевірка статусу кластера
Переконайтеся, що нода перебуває в статусі `Ready`:
```bash
kubectl get nodes
kubectl cluster-info
```
*Очікуваний результат:*
```text
NAME       STATUS   ROLES           AGE   VERSION
minikube   Ready    control-plane   1m    v1.28.x
```

### 3. Розгортання тестового сервісу (Hello World)
Створіть deployment на базі Nginx та відкрийте до нього доступ через NodePort:
```bash
kubectl create deployment hello-world --image=nginx
kubectl expose deployment hello-world --type=NodePort --port=80
```

### 4. Перевірка ресурсів
Перевірте, що всі компоненти успішно запустилися:
```bash
kubectl get deployments
kubectl get pods
kubectl get svc
```

### 5. Отримання доступу до застосунку
Ви можете отримати пряму URL-адресу сервісу:
```bash
minikube service hello-world --url
```
**Або** прокинути порти локально (рекомендовано для Linux Mint):
```bash
kubectl port-forward service/hello-world 8080:80
```
Тепер перевірте роботу застосунку в новому терміналі чи браузері:
```bash
curl http://localhost:8080
```
*Очікуваний результат:* Повернеться стандартна HTML-сторінка з вітанням від **Welcome to nginx!**.

### 6. Очищення середовища
Після перевірки видаліть створені ресурси та зупиніть віртуальну машину:
```bash
# Видалення застосунку
kubectl delete service hello-world
kubectl delete deployment hello-world

# Зупинка кластера
minikube stop
```

## Висновки

**Основна рекомендація:** Для першого PoC стартапу **AsciiArtify** оптимальним вибором є **minikube**. Він найкраще підходить для команди без значного DevOps-досвіду завдяки простому старту, чудовій документації та підтримці аддонів.


### Підсумки по інструментах:

* **minikube** — найкраще рішення для розробки, навчання та швидкої перевірки базових Kubernetes-сценаріїв на старті проєкту.
* **kind** — ідеально підходить для інтеграції в **CI/CD** та автоматизованого тестування Kubernetes-маніфестів.
* **k3d** — чудовий вибір для швидких локальних демо та легковагових кластерів, але через використання спрощеного `k3s` може мати відмінності від повного production Kubernetes.

> 💡 **Резюме:** З урахуванням простоти, якісної документації та низького порогу входження, **minikube** є найкращою стартовою точкою для першого прототипу AsciiArtify.
